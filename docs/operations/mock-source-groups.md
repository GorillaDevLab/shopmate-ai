# Pure incremental source timestamp groups

`createSourceGroupGenerator(config, hydration?)` returns a stateful pure generator with `window(after, until)` and `snapshot()`. Inputs are closed, validated configuration and hydration records; times must be canonical UTC. Windows are `(after, until]`, at most one day. A fresh generator must include opening. Continuations start at the owned `through` position. Only one iterator may consume a generator at a time; exhausting or closing it releases ownership.

`SourceGroup` contains `occurredAt` and owned, deeply frozen `SourceGroupSnapshot[]`. These provider-neutral types use commerce contracts and do not import privileged database ports. Opening emits STORE and PRODUCT baseline snapshots. Existing timeline windows and the bounded causal reducer produce actual ORDER, REFUND and INVENTORY effects, including additive opening/restock balances, reservation, cancellation, shipping and return conservation. No full-history source generator is called in production.

Causal events keep the existing UTF-16 lifecycle ordering. After all effects at a timestamp have been applied, physical snapshots sort by phase (STORE, PRODUCT, ORDER, REFUND, INVENTORY, MARKETING), then UTF-8 bytes of PostgreSQL JSONB entity-key text with comma-space separators. Stable repeated-key effects receive zero-based decimal ordinals. Source versions remain null; sequence allocation belongs to the worker adapter. A group is bounded to 16,384 events and 64 MiB of encoded events.

`createMarketingAccumulator(config, rows?)` consumes accepted PAY effects from the causal reducer. It retains at most one total per configured campaign day (365 maximum), counting actual attributed paid orders and their original paidMinor. Later full/partial refunds do not reduce attributed revenue, matching offline marketing. Lost-demand/no-op PAY and cancellation do not add attribution. The shared campaign row helper preserves deterministic spend, click/impression counters, date and source time. Hydrated MARKETING rows require owned scope/day/date, known counters, canonical source time, complete quality, consistent spend/clicks and bounded daily order totals; foreign, duplicate and inconsistent rows fail.

`observe(at)` considers only the current and previous campaign days: PAY settles within five minutes, so older attribution cannot change. It emits at most two rows whose physical source time equals `at`, including closing midnight and late PAY. Groups use this method rather than regenerate every historical campaign at every event. `snapshot(at)` remains a bounded full hydration DTO. Window end is also an observation point, so partial-day spend is observed without a synthetic paid order.

## Restart contract

Hydration is `{ causal: { orders, inventory, lastEvent? }, marketing, through }`. The worker must load the required accepted records strictly before the timestamp T being reconstructed, including the earlier campaign totals. Set `through` to `T - 1 ms`, omit the causal checkpoint when hydrating database rows, and call `window(through, windowEnd)`. Reapply the complete T group, then let the append packer skip its already accepted physical prefix. Never hydrate mid-T accepted payloads or skip accepted causal effects before deriving the group: either changes downstream inventory and repeated-key ordinals. The pure module has no SQL sequence, lease, append, certificate or background job responsibility.

Live continuations may retain the generator across bounded day windows. `snapshot()` carries the causal checkpoint for pure in-memory restarts, and every hydrated source time must be at or before `through`. Caller mutation cannot alter accepted state or prior emitted groups. Generator snapshots are local progress only; durable resume must use the database worker's accepted checkpoint and strict-before-T hydration.

## Verification and measured limits

Focused API mock tests cover four-profile offline parity across day restarts and delayed settlements, inventory/refund finance conservation, full/partial refunds, partial-day spend, UTF-8 versus UTF-16 ordering, stable same-key ordinals, opening-group restart after a physical prefix, closed/unknown/foreign hydration, caller ownership, concurrent iterator rejection and count/byte budgets. The API privileged-import guard remains unchanged. No UI is introduced.

One local Node 24 run used the mature profile, 180 history days plus five settlement days, dailyOrders 100, 60 products and 180 SKUs. It generated 81,380 groups / 213,752 snapshots in 24,867 ms. Maximum group: 241 events / 126,949 encoded bytes. Maximum retained orders: 606; campaign rows: 180. This measures pure generation only, without DB append, hashing, restart hydration, network or background scheduling, and is not an end-to-end throughput claim.
