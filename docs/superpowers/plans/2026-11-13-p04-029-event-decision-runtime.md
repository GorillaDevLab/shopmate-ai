## Limit of the guarantee

A revocation committed **after** A's final statement snapshot, even before physical COMMIT, need not invalidate A. Ordinary status/role updates, membership delete and connection reset do not take the proposed routing advisory lock. Examples include `demo-commerce.mutations.ts:200–207` (`generation=generation+1,status=...`), `demo-commerce.repository.ts:78–80` (session/connection writer locks) and the actual SQL in `audit-storage.test.mjs:962` and `notification-outbox-cases.mjs:246`. FK key-share locks do not block ordinary non-key status/role updates. Explicit locking SELECT requires update privilege on at least one column; the tested runtime must not gain arbitrary authority-table UPDATE. Even a hypothetical KEY SHARE alone would not conflict with those non-key updates. Repeated SELECTs, a separate transaction or a SECURITY DEFINER predicate with plain SELECT have the same last-snapshot boundary.

029's accepted text requires rejection of current membership revocation; 030's listed races cover dedup, stale evidence, rollback and late decisions (`phase-04.md:1564,1620–1622`). The prepared 029 plan explicitly identifies the final statement as its linearization point. On that wording a physical commit fence is **not required**. Freeze the test ordering and narrow role-read provisioning before claim. If the required contract changes to preventing every revocation from linearizing inside the final-check/commit interval, split a reviewed database guard first: hold conflicting locks through commit for all mutable authority dependencies, including actor/recipient rows, and serialize changes that can introduce a second active connection for the same store. Specify mutation coverage, lock order, restricted definer/owner/RLS grants, timeout and both interleavings. Existing read roles and routing locks cannot establish that stronger claim within the current no-migration slice.
