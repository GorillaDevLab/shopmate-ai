# P03-019 publication lineage clarification

Task 2 contract clarification reviewed by the coordinator before implementation. The approved November 11 design requires immutable fact versions, server-certified scope and coverage, atomic append and sealed historic replay. It leaves the publication sequence and repeated membership encoding to the contract. Use a complete partition snapshot per publication. A later certificate can include an already-stored fact version in its original form. This fits the existing single-publication COMPLETE coverage proof.

## Three independent sequences and identities

| Value | Meaning |
|---|---|
| `ObservedPublicationRequestV1.expectedSequence` and returned `ObservedPublicationV1.publicationSequence` | Positive safe integer publication ordinal for `(full binding, generation, domain, subject, window)`. First seal is 1. A new seal advances the ordinal by one under publisher authority. An identical publication request retried after success resolves to the existing certificate for that ordinal and exact certified content/cutoff. A different seal at an occupied ordinal or an attempt to skip an ordinal is a conflict. The pinned model/config belong to generation identity. The ordinal is included in the certificate hash. |
| `fact.sequence`, `fact.sourceVersion`, `fact.priorVersion` | Source position assigned when a new immutable observation version is produced. The version carries the generation and positive safe source sequence. Within the bound generation/domain source stream, a new position identifies one original fact/version. Different subjects/windows can select sparse positions. A correction gets a fresh position and points to the previous version of the same fact. Repeating an exact existing version in another snapshot consumes **zero** new source positions. |
| `pageIndex`, `expectedCursor`, `priorPageHash` | Page position, cursor and hash chain within one publication. Indices start at 0. Every record is strictly ordered by its original source sequence across pages, with no duplicate selected logical fact or source version in a complete snapshot. A page-chain gap is invalid. Source-position gaps in a sorted snapshot are expected when a predecessor is superseded or other subjects occupy intervening positions. |

Task 2 uses `publicationSequence` for the certificate ordinal. Do not couple page records' original source positions to that ordinal. Source-chain certification checks the authoritative selected versions through the business cutoff. Page numbering and the publication ordinal independently retain their contiguity requirements. A zero-member snapshot has an ordinary publication ordinal and one terminal zero-row page. No minimum fact source sequence is needed.

## Durable origin and page membership

Retain `StoredObservedFactV1 {fact,receiptId,recordedAt}`. Its `receiptId` always points to the first committed receipt that inserted this exact fact version, and `recordedAt` is that immutable fact's DB insertion timestamp. Both stay fixed across future captures. The reader returns these fields from the stored record.

In **returned consumer receipts only**, extend each `ObservedReceiptV1.factRefs[]` element to `{factId,sourceVersion,payloadHash,originReceiptId}`. The enclosing receipt identifies this page membership. On first insertion, originReceiptId equals the enclosing receiptId. On exact-version replay into a **different certified page**, the new receipt contains a reference to the original receiptId. The DB assigns originReceiptId and verifies the original stored record. Keep this field out of worker inputs, immutable source payloads and publisher page preimages; it exists only after atomic append. `recordCount` counts certified page members, including exact-version repeats. The number of newly inserted facts may be lower. The publisher hashes the canonical source page and certificate; the capture separately binds the returned membership/origin edges.

For an existing version, check canonical equality of the **entire immutable fact** including binding, subject, both business instants, priorVersion, producer/model versions and payload, as well as its ID/version/hash. A matching payload hash alone does not establish equality of the envelope. For a different fact version, validate prior linkage before admitting a new fact. A consumer lacking a required predecessor needs the original certified history to resolve that dependency. Retries of the **same** page/hash under current authority return its original page receipt and never create additional membership or facts; divergent retries conflict. Stale pages cannot overwrite selected versions. A repeated source fact may be first accepted by a different receipt depending on actual commit order. The stored origin always follows the first real insertion.

## Capture checks

1. Each COMPLETE coverage row still lists the ordered chain of exactly one certificate for its partition. The union of that chain's page members is the certified visible set. Resolve each member to exactly one selected stored version for that coverage, check the domain/subject/window eligibility, version/hash and unique logical fact, and reject extra or missing members. The service selects the authoritative available snapshot for that cutoff. Supplying matching counts and hashes cannot establish its authority through schema parsing alone.
2. Independently resolve `stored.receiptId == membershipRef.originReceiptId` in the capture's `receipts`. That origin receipt must itself contain the exact factId/sourceVersion/payloadHash and a self-origin reference. Both receipts resolve to certificates in `publications`; verify the original fact's observedAt against both certificates' through cutoffs and the capture's visibleAt. Validate each receipt against **its own** publication's binding/generation/domain/subject/window, producer, model/config/hash and availability. Origin scope/domain/subject must match the stored fact. If an eligible retained-history fact has its origin in an earlier window, that earlier partition demonstrates origin only. COMPLETE coverage still comes entirely from the selected certificate for the exact requested window. Keep all measurement-window eligibility checks.
3. Include the deduplicated union of coverage and required origin receipts/certificates in the sealed evidence graph. Origin receipts may also contain earlier, superseded versions. Their presence does not select those old members. For this partition `coverage.receiptIds` and the scoped selection's coverage proof use the **current snapshot's membership receipts**. Immutable source provenance remains reachable from each selected membership's originReceiptId. Hash both relations, membership identities/receipt hashes, original stored version/hash and selected coverage into the joined revision. For historic replay use the original sealed graph and revalidate current reader authority.
4. P03-020 stores the immutable origin and receipt memberships. P03-035 certifies the full visible set through a verified business clock for one partition, with original fact bytes for unchanged members. P03-021 deduplicates immutable versions, inserts memberships and advances cursor/receipt atomically. P03-022 resolves both edges when sealing or replaying. A producer can emit mixed subject/domain batches; P03-035 partitions and validates them before sealing. One COMPLETE proof covers one subject/window/domain. Preserve existing bounds and return OVERFLOW if a snapshot or the necessary proof exceeds them.

## Two-publication contract fixture

Use the plan's five-part binding, generation 0, subject SKU sku-A, domain FROZEN_COST, one fixed W = [2026-11-01T16:00:00.000Z, 2026-11-02T16:00:00.000Z), CNY/Asia/Shanghai. Define T1 = 2026-11-02T16:00:00.000Z, T2 = 2026-11-03T16:00:00.000Z. Pin the same producer/model/config for both publications, each with pageIndex 0, null cursors and priorPageHash, terminalCoverage 10000, pageCount 1, recordCount 2 and through=availableAt=T1 or T2 respectively. Use distinct SHA-format synthetic page/publication hashes and appropriate four-stream base refs for each financial capture. Use "a","b","c" repeated 64 times as the three payloadHash fixture values; fixtures model structure only. Use an arbitrary later security-clock sample for each independent DB write.

|---|---|---|
| A1 | factId A, sourceVersion observed-v1:g:0:e:1, priorVersion null. Order oA/line lA, quantity 1, confirmed cost 100 cost-v1, occurredAt/frozenAt/observedAt T1, payload hash a×64. | R1 |

At T1, request expectedSequence=1. P1 publicationSequence=1 certifies [A1,B1]. R1 membership refs are [(A,1,a,R1),(B,2,b,R1)] (abbreviated source versions/hashes). Capture C1 selects [A1@R1,B1@R1], graph receipts [R1], coverage [R1]. Preserve C1's joined revision.

At T2, request expectedSequence=2. P2 publicationSequence=2 certifies [A1,B2] in source order [1,3]. The first member's source position is **1**, A's original observation and all its bytes are unchanged. R2 membership refs are [(A,1,a,R1),(B,3,c,R2)]. C2 selects stored [A1@R1,B2@R2] with original DB-recordedAt for A1. C2 graph publishes [P1,P2], receipts [R1,R2], current complete coverage [R2]. B1 is reachable under R1 and is excluded from C2's selected set. Exactly three fact versions and four memberships across both pages. Subsequent replay of C1 still selects only [A1@R1,B1@R1]. This works with existing three-key ScopedMetricInputV1 and requires no new sourceVersion for A.
