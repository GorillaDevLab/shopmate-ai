# Demo scenario management delivery

1. Scope: completion-plan unit 5 management API/storage for synthetic demo tenants. Source-worker and sync-host processes are unchanged.
2. Endpoints: authenticated `GET /api/v1/demo-commerce/stores/:storeId/session/scenarios` and same-origin `POST .../scenarios/load`. Requests select one of fifteen scenario IDs and optional bounded day window; client-provided scope or mutations are rejected.
3. Confirmation: load requires current session ID, expected revision and expected connection generation. Only current OWNER/ADMIN access can write. Production markers, foreign merchant contexts, revoked memberships and assigned viewers cannot load.
4. Persistence: each load stores the complete strict owned configuration and canonical hash in immutable `DemoScenarioRun`, with full organization/workspace/store/session/connection/external-store binding. Plans inherit current session settings; reset supplies a fresh baseline when desired.
5. Fencing: load follows CONTROL → session → connection locks, increments connection generation and session clock/revision, and never overwrites accepted Runtime snapshots. Old leases and generation reads immediately lose current authority.
6. Time: PostgreSQL assigns `loadedAt` from its UTC wall clock, overriding supplied values. `businessClock` records the independently controlled initial simulation instant. API, repository and SQL reject times outside history start through the configured five-day settlement horizon.
7. Audit: a trigger inserts an immutable run snapshot audit; the existing RESET control audit records the resulting revision/generation/config hash. Suppressed audit insertion rolls back configuration, generation and run rows together.
8. Lifecycle: existing session advance/reset/disconnect and failure-rule controls manage the run. Reads return the latest twenty runs and derive ACTIVE/SUPERSEDED/DISCONNECTED from current generation, connection status and frozen configuration. ACTIVE means configured, not source publication or sync completion.
9. Migration: additive `20261009100000_demo_scenario_runs` enables and forces RLS on runs/audits, uses invoker-rights authorization and rejects direct audit forgery/history mutation. Source reader/worker roles receive no management grants. Deployment must grant the existing trusted demo management login SELECT/INSERT on both new tables and EXECUTE on `demo.has_scenario_access(TEXT,TEXT,TEXT,TEXT,TEXT,TEXT,INTEGER,BOOLEAN)`; retain its existing session/control permissions. No online migration ran.
