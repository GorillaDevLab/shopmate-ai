# P2.4–P2.5 remaining execution plan (working draft)

Scope: synthetic Chinese SME commerce data only. Existing four offline profiles, read-only connector, demo session and deterministic read faults are foundations, not completion. Do not call real platforms, Jev or LLM; defer deployment and online migration. P3+ implementation belongs to the human agile pool.

## Dependency order and PR units

1. **Source publication closeout (#439).** Finish official publish and certificate-read ports, exact retry/current authority and restricted-login tests; resolve local lease-bound gate discrepancy, whole-branch review and latest CI before merge. A certificate proves physical accepted-prefix completeness, not business completeness.
2. **Persistent source scan.** From an authorized published certificate, provide fixed-window keyset reads of own entity versions, pin `(scope, generation, certificateHash, highEventSeq, until)`, page by stable kind/key/event order, and require current authorization on every page. A restart-safe opaque cursor must be integrity protected with an environment key and strict size/expiry bounds. No staged rows or source events leak. Test restart, advance/reset, revocation, namespace tampering, equal-time ordering and 375/empty/error API states only if an actual UI is introduced.
3. **Persistent read-only CommerceConnector.** Adapt the existing connector interface to scan-backed records rather than regenerate the entire history on demand; preserve all thirteen methods and unsupported writes. Factory resolves current DemoSession/Store/connection/merchant and chooses the persistent adapter; checkpoint/certificate bind every read. Test pinned pages and point reads under advance, expired cursor, denied/foreign scope, partial quality and retry.
4. **Incremental causal generator host.** Bounded background claim → deterministic next slice → append → publish using frozen source configuration and checkpoint. Persist enough progress to resume a lease after process restart without regenerating or overwriting accepted history; never do CPU generation inside a locked DB transaction. Reuse existing causal generator where semantics match; explicitly reconcile frozen opening/target and same-time event ordinals. Test crash before/after append acknowledgement, takeover, advance, reset, conservation and reproducible hash.
5. **Scenario engine and management.** Persist scenario run/configuration in demo-only protected storage; make load/advance/fault controls authenticated and safe against production merchant contexts. Runtime sees only causal mutations; expected events/reasoning/decisions stay test-only. Implement all 15 scenario manifests and observable mutations/negative controls, including quality uncertainty, seasonal baseline, duplicate/late delivery and concurrent problems. Demonstrate source/connector observations, not P3 Event Engine conclusions.
6. **Failure rule management.** Build authenticated demo-only rule creation/removal/expiry on the existing deterministic read-fault mechanism; bind tenant/store/session/generation, enforce precedence/limits and audit state changes. Cover timeout/rate limit/permission/error and read-only delayed consistency where the port supports it; P8 write-ack ambiguity remains later scope.
7. **P2.5 durable sync host.** Persist per-scope stream/window/cursor/status/lease/watermark and page ingestion into normalized tenant data using the generic CommerceConnector contract. Use stable idempotency keys and source versions; atomically persist rows and cursor progress, retry bounded failures, quarantine invalid records with counts. Lock one worker per store/stream and recover after crash. No provider-specific branch in business ingestion.
8. **Out-of-order/dedup and freshness.** Replay duplicate pages/events without duplicate facts; older versions never replace newer; late corrections are applied only under explicit version/time rules. Expose per-stream successful-through watermark, observed-at and lag/status so stale/unknown is distinct from zero revenue. Test scenario 009/010, delayed pages, torn acknowledgement, reset/new generation, and two-tenant access boundaries.
9. **Phase acceptance.** Four profiles and 180-day configured history (new store 14 days) through persistent connector; all 15 scenario outcomes/negative controls and causal invariants; full source→sync counts, fixed-window no-gap pages, restart recovery, tenant isolation, load/empty/error operational states, selected performance benchmark with actual measured limits. Update tracker and 12-field delivery reports with exact gates; latest CI/independent review for each PR.

Every unit: fail-first critical test, implementation, focused gate, review, independent clear commits, PR/attach, latest-head CI and authorized merge. Avoid claims that P3 metrics/event/agent/approval logic already exists.
