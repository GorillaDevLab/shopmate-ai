# P2 incremental source worker

1. **Scope:** persistent synthetic commerce generation for approved demo sessions. No platform, Jev, LLM, deployment or live migration is included.
2. **Process:** `@shopmate/source-worker` discovers current granted scopes, initializes frozen configuration, claims a backend lease, generates outside SQL transactions, appends bounded chunks and publishes a sealed source revision. `start:once` processes one pass; `start` polls every five seconds.
3. **Environment:** require `APP_ENV=demo`, `ENABLE_DEMO_MODE=true` and a separate `MOCK_PLATFORM_WORKER_DATABASE_URL`. The login must satisfy the existing restricted source-worker checks; there is no application database fallback. Stop on SIGINT/SIGTERM, release interrupted work and close the pool. Diagnostics expose a fixed failure code.
4. **Recovery:** hydrate actual accepted state strictly before checkpoint time and replay the entire boundary timestamp. The chunk packer excludes the accepted prefix. A lost append response preserves durable progress; an already sealed recovered job publishes without regenerating facts.
5. **Bounds:** one-day generation windows, a bounded active order tail, at most 5,000 hydration keys in batches of 100, and 80 events per normal append. Larger timestamp groups remain bounded and split without losing their tail. The existing 100-event, 2 MiB append envelope and 30-second lease limits remain unchanged.
6. **Ordering:** causal transitions retain their original ordering; physical snapshots follow the canonical kind/key/time/ordinal ordering. Initial opening records are included even when the first requested target lies after opening. Adjacent small timestamp groups share a transaction.
7. **Authority:** initialization, claim, renew, hydration, append and publication each use current server grants and the complete session generation. Revocation or fencing stops work; accepted unpublished rows stay invisible to source readers.
8. **Storage performance:** ordered bulk inserts replace repeated per-event statements. Migration `20261009070000_source_auth_cached_plans` changes three identical authorization predicates to cached PL/pgSQL execution plans, preserving ownership, privileges, invoker security and volatility. Calls continue evaluating live identities and data; authorization results are not cached.
9. **Actual measurements:** before optimization, the 401-record opening recovery test took about 318 seconds. With bulk inserts, cached plans and bounded batching, the recovery test took about 23 seconds; the expanded recovery plus two clock advances, continuous-generation comparison and revocation test took about 34 seconds. A separate 100-event append measured 1.97 seconds and publication 47 ms. These are local fixture measurements, not 180-day phase acceptance.
10. **Verification:** meaningful fail-first chunk-budget and batching tests; unit coverage for sealed recovery, boundary replay, shutdown and full active-tail hydration; real restricted PostgreSQL lost-ACK recovery, two incremental revisions matching every latest causal fact, and revoked-grant refusal. Bulk suppressed-row rollback and warmed-backend identity/grant/reset regressions are mandatory in tenant CI.
11. **Compatibility:** v1 frozen source configuration and the read-only connector remain unchanged. The new application imports a pure generation export from the API package; business API code receives no privileged source-worker port.
12. **Remaining P2 work:** scenario configuration/management and operational delivery controls, durable generic sync completion/freshness, four-profile 180-day source-to-sync acceptance, and final independent review/latest-head CI. A source publication proves its accepted physical prefix, not successful downstream business synchronization.
