# P04 event and evidence storage

The forward-only `20261025090000_events_evidence` migration adds empty event and immutable evidence tables after the P03 metric migrations. It implements the storage boundary for the frozen P04-001 `EventRecord`, `EventEvidenceRecord`, and evidence references. Repository, lifecycle/CAS services, controllers, provider calls, application login provisioning, deployment, and production migrations remain outside this card.

## Identity and history

`EventRow` maps to `events`. It stores the five-part connector binding, schema version, event type/entity, nullable baseline version, canonical fingerprint, deterministic severity floor, rule policy version, state/revision, first/last-seen instants and current evidence ID/version/hash. The fingerprint is the exact JSON serialization of `[event-fingerprint-v1, organizationId, workspaceId, storeId, eventType, entityKind, entityId, baselineVersion]`. Connection identity intentionally does not participate in deduplication, but all history references still bind connection and external store ownership.

`events_active_fingerprint_key` is a PostgreSQL partial unique index for `OPEN`, `ACKNOWLEDGED`, and `SUPPRESSED`. Separate concurrent transactions cannot create two active occurrences. `RESOLVED` rows retain history and permit a new occurrence with the same fingerprint. The scope/history index supports ordered tenant reads. Database constraints check event/entity compatibility, known states/severities, the product-breakout severity ceiling, literal IDs/versions, safe positive revisions and finite ordered times.

`EventEvidenceRow` maps to `event_evidence`. Each revision stores its event/binding/fingerprint, evidence ID/version/hash, schema/definition versions, period, observation/watermark instants, fixed timezone/currency, explicit quality columns and the supplied evidence payload. There is no fabricated payload default. `(eventId, evidenceRevision)` is unique. Appending a new revision or reusing an existing same-hash reference does not rewrite old evidence. Event identity/first-seen time cannot change; revision and last-seen time cannot decrease. Evidence and association UPDATE, DELETE and TRUNCATE are rejected by triggers, even for operator DML. Event DELETE/TRUNCATE is also denied. Trusted DDL administrators can alter constraints; trigger immutability is not protection against administrator DDL.

The current-evidence composite FK includes evidence ID, event ID, all five binding fields, fingerprint, version and hash. It is `DEFERRABLE INITIALLY DEFERRED` so a transaction can insert an event and its first evidence together, or append evidence before advancing the pointer. Commit fails without a matching immutable reference. Store and platform-connection composite FKs reject mixed ownership. All relations use `ON DELETE RESTRICT ON UPDATE NO ACTION`.

`EventEvidenceMetricRow` maps to `event_evidence_metrics`. This append-only join associates each evidence revision with any number of metric snapshots. Both endpoint FKs include all five binding identifiers; cross-organization, workspace, store, connection or external-store links fail. There is no unprotected metric UUID array. The future repository must materialize metric source references into this relation in the evidence transaction; JSON source references are descriptive evidence, not authority to fetch a metric outside the checked relation.

## Validation boundary

The database checks schema version 1, nonempty literal versions/hashes, bounded safe integer sample/revision values, finite time ordering, a positive half-open period, `Asia/Shanghai` and `CNY`, and nullable watermark semantics. `VERIFIED` requires full coverage, no issues and a watermark covering period end. Every other quality status retains nonempty valid issues. Evidence payload identity, binding, definition/baseline versions, observation/period/watermark, quality and source-reference scope must agree with the relational envelope. Nullable baseline values, including versioned `MISSING` baselines, remain representable.

The SQL checks validate the persisted envelope; they do not replace the discriminated `EventEvidenceV1Schema` host parser or domain-specific facts, baseline arithmetic and hash verification. Before persistence, the future repository must strictly parse the complete frozen contract, verify authorized source facts and recompute the canonical evidence hash. Hashes here use the contract's opaque literal identifier semantics, not an invented digest format. No SQL check manufactures a completeness or provider-authority proof.

## Capabilities and tenant context

The migration creates `shopmate_event_reader` and `shopmate_event_writer` as restricted `NOLOGIN NOSUPERUSER NOBYPASSRLS` capability groups. It grants no application login membership or credentials. Both groups can SELECT the three tables. The writer can INSERT and update only event state/revision/last-seen/current-reference columns. Neither receives DELETE/TRUNCATE or evidence mutation permission. PUBLIC receives no table privileges or helper-function execution rights.

All three tables enable and force RLS. Authenticated application transactions must use READ COMMITTED and set `app.user_id`, `app.organization_id`, `app.workspace_id`, `app.store_id`, `app.connection_id`, and `app.external_store_id` locally from server-resolved ownership. Missing or mismatched context defaults to denial. `event_scope_access` is a narrow boolean SECURITY DEFINER predicate with `search_path=pg_catalog`; its owner must bypass forced tenant RLS and it returns no raw tenant rows. Current active organization, workspace, organization membership, store merchant ownership, and full platform connection ownership are rechecked on each statement.

OWNER/ADMIN may manage the organization scope. OPERATOR may manage only a currently assigned active workspace. ANALYST/VIEWER have read access in their currently assigned workspace. This event-specific predicate intentionally differs from the OWNER/ADMIN-only metric write predicate. Removing membership or assignment immediately removes access; repeatable-read/serializable tenant access is denied to avoid stale authorization snapshots.

## Prisma and migration verification

Prisma mirrors every new column, nullability/type, ordinary index and composite relation, including the scoped metric join and supporting metric unique key. The partial active-fingerprint index, deferred FK timing, checks, triggers, collations, capability roles and RLS are SQL-owned features Prisma cannot express. They are not excluded from drift checks or hidden behind ignored models.

`packages/database/test/integration/event-storage.test.mjs` is explicitly registered in `scripts/test-tenant-database.mjs`, independently of the default `test/*.test.mjs` glob. `pnpm test:tenant` starts and stops disposable local PostgreSQL, removes inherited database/PG environment variables, and injects only runner-owned isolated URLs. Every registered database target must report positive TAP tests with zero failures/cancellations/skips/todos; every required API target must report positive passing assertions.

The focused tests cover fresh and populated upgrades, envelope rejection, immutable revisions, full binding FKs, restricted writer inserts, live RLS membership, real separate-client active uniqueness with bounded lock waits, resolved recurrence, Prisma deployment and an empty schema diff. The existing metric populated-upgrade test defers the dependent event migration alongside metric migrations, then restores them in dependency order while preserving its prior history and drift checks. No deployed or production database is touched.
