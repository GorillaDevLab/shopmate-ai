# P2 持久源到同步运行器交付

1. **交付范围。** 当前数据全部为合成经营数据；本次交付打通已发布源 → 同一 CommerceConnector 契约 → 持久同步任务 → 标准化经营事实。P3 Metric Engine、P4 Event Engine、Jev/LLM、真实平台、审批写执行和部署不在本次范围。本文的验收记录不代表已经上线。
2. **可运行入口。** `@shopmate/source-worker` 按当前授权发现工作，分六小时发布源历史；`@shopmate/sync-worker` 提供 `start` 和 `start --once`，协调五类流、读取真实持久页并原子提交。两者均要求 `APP_ENV=demo`、`ENABLE_DEMO_MODE=true`；源写、源读、同步宿主使用各自受限数据库身份。同步进程另外要求 `SYNC_WORKER_GRANT_ID`、`SYNC_WORKER_DATABASE_URL`、`MOCK_PLATFORM_READ_DATABASE_URL` 和环境中的 `MOCK_SOURCE_CURSOR_KEY`。
3. **身份与代边界。** 服务端从 worker grant 派生 principal、merchant 和完整七字段源 scope，CLI 不接受调用者选择的租户、商家或目标时刻。每次发现、取页、创建窗口、提交和重放重新检查权限。reset/load 产生新 generation，旧任务、游标和授权不能被静默搬过去；受信配置身份需提供匹配新 generation 的同步 grant，再启动新进程。应用身份不承担迁移或 grant 配置权限。
4. **协调与分页。** 五个流共享实际业务时钟、已验证发布覆盖和各流起点加 31 天的最小目标。未完成窗口固定原目标，重启继续持久 cursor/pageCount。每个 runner 只保留自己实际获得的同后端租约，不能把 RUNNING 字样当成所有权。全快照产品、订单、退款和库存不传增量 since；营销从已验证经营起点读取。
5. **原子与恢复。** 每一页的事实、版本决策、隔离记录、receipt 和 cursor/progress 在一个数据库提交中落地。业务 page ID 使用持久页数；签名过期的 continuation 按原证书、查询和见证恢复，不能跳到新快照。提交回执丢失作为未知错误传播，重启读取实际已提交状态，不重新取页或制造失败。
6. **中断场景 009。** LOAD 的不可变 run.businessClock 是中断起点，生效区间为 `[起点, 起点 + durationMs)`，按持久业务时钟判断。五个分页方法返回 TEMPORARY，getStore 不被中断；不会在真实时钟上等待一小时。重启不重置期限，advance 到精确结束边界恢复原窗口。该配置保留一个规则槽和 priority 1000，托管规则最多 31 条；合计最多 32 条，命名冲突、越界和超额显式拒绝，不丢弃规则。
7. **重复与延迟场景 010。** 第一页的原始编码字节、page ID、原 cursor 和作用域在原提交事务内保存，每个 run/stream 最多选择一次，额外次数为 1–3。后续页已提交后或任务终结后，重放同一个原 envelope；重放与尝试序号 ACK 原子完成。即使所有流已追平，重启也发现并处理待重放页。RUNNING 重放只续期显式属于当前后端的租约；外来或已过期租约返回 BUSY，让普通 runner 正常处理。重放结果不覆盖当前 runner 进度。
8. **停止、故障和质量。** 一次 pass 共用原始绝对截止时间；只读发现、选择和取页支持 deadline/abort，停止后不继续启动变更。原子变更等待真实 ACK，不能因暂停虚构成功或失败。仅实际 TEMPORARY/TIMEOUT/RATE_LIMIT 结果有限重试；权限、代漂移、未知存储错误传播。成功覆盖、observedAt、sourceWatermark、状态和质量缺失均保留；未知成本/退款/库存不能被解释为零。
9. **实际验收。** 真实 PostgreSQL 覆盖：过期游标重启、终结 ACK 丢失、五流认证空覆盖、取页后撤权、取页后停止、共同目标与续租、真实 CLI；009 的 LOAD/中断/重启/expiry/规则容量/撤权/reset；010 的真实多页、晚页和终结重放、保存回滚、原 ACK/重放 ACK 丢失、真实进程退出、租约交接、旧窗口、外商家、撤权/reset/disconnect。15 个场景均经过真实 LOAD、持久源发布、Connector 和五流标准事实验收；期望事件或 Agent 推理只在测试中，P2 不输出 P3/P4 结论。
10. **已测规模与限制。** 成长/问题/成熟画像各配置 180 天经营历史，以 2 单/日、6 产品和 18 SKU 验证全历史链路；各 540 个订单，退款分别 20/37/8，营销各 180 条。完整四画像本机验收约 31.6 分钟。新店默认量单独验收：配置 180 天、实际经营 14 天、6 单/日、60 产品、180 SKU、66 订单/订单行、1 退款、180 库存、14 营销，源事件 1,098；最近一次约 115 秒。嵌套 SKU 的属性、价格和 nullable cost，以及订单行身份、数量和金额，与源完整比较。此前高负载源基准为 100 单/日、五天经营加五天结算，40 个六小时发布前缀、4,666 事件，约 413 秒。默认成长画像 180 单/日贯穿 180 天和 365 天容量未据此宣称通过；默认配置保持 60 产品/180 SKU 和各画像原数据量。长历史初始构建应在后台预热，演示时读取已发布且已同步的覆盖。
11. **迁移与门禁。** 新增有序迁移 `20261009140000_sync_scenario_delivery`、`20261009150000_sync_scenario_interruption`，保存表强制 RLS、禁止直读写与内容更新；SDK 只暴露受授权函数。未执行任何线上迁移。普通质量门禁强制执行恢复、009/010 PostgreSQL 套件；另有四画像矩阵和 15 场景完整链路 CI job，不以跳过或 continue-on-error 放行。最新完整 CI、独立任务审查和整体分支审查全部通过是合并条件。
12. **P3 接续。** 后续开发读取 `commerce` 的 Product/Sku/Order/OrderLine/Refund/Inventory/CampaignMetric 标准模型，使用整数分、nullable 值、质量 issues 和源版本；沿用当前身份/RLS，不能在 Metric Engine 中重新生成 Mock 或引用场景预期结论。同步宿主提供真实覆盖和进度；API/前端经营指标、事件决策、证据链和审批执行沿已批准任务池继续。部署、配置身份、受限登录与 grant 初始化由用户后续统一执行；迁移失败记录应按现有恢复文档处理，不能提高应用权限或清除未知失败记录。
